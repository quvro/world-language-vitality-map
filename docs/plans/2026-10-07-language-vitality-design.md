# 「正在消失的声音」——数字时代的语言生存图谱

**数据可视化与人机交互 · 课程项目设计文档**
日期：2026-10-07

---

## 0. 项目定位：先解决"不好讲"的问题

你提出的顾虑很准：**语言学的特征分类很好看，但不好展示、不好讲解。**
根因是——如果把"192 个语法特征"当主角，观众不知道你在讲什么，每个特征都要解释一遍。

**解法：换主角。** 让"语言学特征"退到解释变量的位置，把**"语言的生存状况"**推上前台。

### 叙事主线

> 全球约有 7000 种语言。但在互联网上，只有约 360 种拥有维基百科版本；
> 而 AI 大模型真正"说得好"的语言，两只手数得过来。
>
> 我们把三种数据叠在一起，回答一个具体问题：
> **什么样的语言，正在数字化的浪潮里被抛下？**

| 维度 | 数据 | 回答的问题 |
|---|---|---|
| **结构** | WALS（192 特征 / 2,660 语言） | 这门语言"长什么样" |
| **数字活力** | 维基百科 10 年月度时间序列 | 它在互联网上"活得好不好" |
| **文化与生态** | D-PLACE（约 1,300 个社会） | 说它的人"怎么生活" |

### 可以拿去 pre 讲的四个现实问题

1. **语系之间的数字鸿沟有多大？**——欧洲语系 vs 非洲/大洋洲语系的内容体量差距
2. **过去 10 年，谁在涨、谁在退？**——已实测到的反转：德语浏览量 11.98 亿 → 7.80 亿（↓），
   斯瓦希里语 112 万 → 137 万（↑）。大语种被通用平台分流，小语种在"补课"
3. **语言的结构特征是否影响它的数字化命运？**——有文字传统、形态简单的语言是否更容易获得数字内容
4. **AI 时代的新不平等**——低资源语言在大模型里的缺席，和它们在维基百科上的缺席高度重合

> 有了这四条，每个可视化都在为一个可以讲出口的结论服务，而不是"展示我画了很多图"。

## 2. 数据层设计

### 2.1 数据源（均已实测可获取）

| 数据集 | 规模 | 获取方式 | 状态 |
|---|---|---|---|
| WALS `values.csv` | 76,475 行 | GitHub blob API | ✅ 已验证 |
| WALS `languages.csv` | 3,573 行，其中**真语言 2,662 行**（另 911 行是语系/语族/语支层级占位行，P1 实测发现） | 同上 | ✅ 已验证 |
| WALS `parameters.csv` / `codes.csv` | 192 特征 / 1,139 取值 | 同上 | ✅ 已验证 |
| Wikimedia 浏览量时间序列 | 247 语言 × 127 月 | `wikimedia.org/api/rest_v1` | ✅ 已验证 |
| Wikimedia 编辑量时间序列 | 同上 | 同端点 `/edits/` | ✅ 已验证 |
| Wikidata ISO 639-1↔639-3 | 185 组 | SPARQL（限流 1 次/分，只需 1 次） | ✅ 已验证 |
| D-PLACE | ~1,300 社会 × 数千变量 | `D-PLACE/dplace-data` | ✅ 确认存在 |
| Glottolog 濒危状态 (AES) | 语言健康度 | `glottolog-cldf` | ✅ 确认存在 |

### 2.2 组合后规模

```
可连接语言 247 × 时间点 127  = 31,369 条时间序列
WALS 结构数据                 = 76,475 条
────────────────────────────────────────────
合计                          ≈ 107,844 条
```

**约为 1 万条要求的 10 倍**，且随 D-PLACE 接入会进一步上升。

### 2.3 数据库设计（落地 SQLite）

```
fact_language_feature   语言 × 特征 × 取值      ← WALS values.csv
fact_language_timeseries 语言 × 月份 × 浏览量/编辑量 ← Wikimedia
dim_language            语言主表（经纬度/语系/ISO码/AES）
dim_feature             特征定义（192 个）
dim_code                特征取值定义（1,139 个）
dim_society             社会/文化变量（D-PLACE，第三阶段）
xref_iso                语言代码映射（639-1 ↔ 639-3 ↔ Glottocode）
```

全部是标准 CSV → SQLite 导入，**处理难度低**，且关系清晰可 join。

### 2.4 已知脏数据（真金白银踩过的坑）

1. **WALS 两个数据集字段名不一致**：`values.csv` 用 `Language_ID`，`languages.csv` 用 `ID`，
   关联时不能同名字段直连。
2. **维基百科代码混用两套标准**：`ace`/`ady`（639-3）与 `de`/`ja`（639-1）混杂。
   不走映射表会漏掉 131 个语言（116 → 247）。
3. **`*.wikipedia.org` 在本机不可达**：只能走 `wikimedia.org/api/rest_v1`，
   拿不到 siteinfo 条目数，用"浏览量 + 编辑量"两条时间序列代替。
4. **`github.com` / `raw.githubusercontent.com` 不可达**：必须走 `api.github.com` 的 blob 接口。
5. **Met 博物馆 API 的搜索端点已下线**（410）——虽然本项目不用，但记录备查。

## 4. 技术框架与组件库选型

### 4.1 核心原则：**难画的图交给库，签名的交互自己写**

你的要求是"能细调、不能太模板化"。这两件事其实不冲突，关键是**分工**：

- **交给库**：地图、桑基图、主题河流、平行坐标、热力图——这些手写要几周，且和"是否模板化"无关
- **自己手写**：**时间轴回放**和**条件对比**这两个签名交互（用 D3）——这才是让作品看起来原创的地方
- **绝不用库默认主题**：ECharts 默认蓝是国内大屏的"模板感"来源，必须注册自定义主题

### 4.2 推荐栈

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | **Vue 3 + Vite + TypeScript** | 与老师给的参考技术栈一致 |
| 状态 | **Pinia** | 全局筛选状态驱动所有视图联动，是 Brushing & Linking 的中枢 |
| 统计图 / 地图 / 桑基 / 河流 / 平行坐标 | **Apache ECharts**（自定义主题） | 覆盖最广，地图与平行坐标开箱即用；老师手册也首推 |
| 关系网络 / 语系树 | **D3.js**（d3-hierarchy / d3-force） | 定制自由度最高，树的形态完全自己控 |
| 签名交互（时间轴、条件对比） | **手写 D3 + CSS transition** | 这是"不像模板"的关键 |
| 自然语言查询 | **DeepSeek / GLM API**（Function Calling） | 成本低，中文好 |
| 数据库 | **SQLite** | 课程作业规模足够，join 方便，且"像数据库" |

### 4.3 关于"组件库"的明确建议

**不要引 Element Plus / Ant Design Vue 这类重型 UI 库。** 它们会立刻带来"后台管理系统"的观感，
而且默认样式越多，你要覆盖的 CSS 就越多，反而更累。

推荐的替代方案：

- **布局与组件自己写**：本项目只有 5~6 个视图模块，自己写比覆盖样式快
- 若确实需要无障碍/交互复杂的组件（下拉、弹层、滑块），用 **headless 组件**（如 Radix Vue），
  它们不带任何样式，外观 100% 归你控制
- **必须引的只有可视化库**（ECharts + D3）

### 4.4 "去模板化"检查清单

- [ ] ECharts 注册自定义 light 主题，改掉默认配色/字体/网格线
- [ ] 建立 **design token 层**（CSS 变量），图表从 token 读色，不写死 hex
- [ ] 字体：中文用思源黑体/苹方，数字用等宽或 tabular-nums（大屏数字对齐才对味）
- [ ] 关掉 ECharts 默认动画，改成与页面节奏一致的缓动
- [ ] 时间轴与条件对比两块用 D3 手写，不用现成组件
- [ ] 全站统一圆角/阴影/间距尺度（发 token 定义），避免各处不一致

## 6. 导航设计与信息架构

对应老师注意点 2。采用**单页多视图 + 全局状态驱动**，不做多页面跳转。

```
┌──────────────────────────────────────────────────────────────────┐
│  ◉ 正在消失的声音     [故事模式 | 探索模式]      [语系▾][地区▾]  │  ← 顶栏
├────────────┬──────────────────────────────────────┬──────────────┤
│            │                                      │              │
│  筛选面板   │            主视图区                   │   详情面板    │
│            │   （可切换：地图 / 时间轴 / 矩阵 / 树）  │              │
│  语系树     │                                      │   语言卡片     │
│  ├ 印欧     │                                      │   · 结构特征   │
│  ├ 汉藏     │                                      │   · 10年曲线   │
│  └ 南岛     │                                      │   · 文化背景   │
│            │                                      │              │
│  特征选择器  │                                      │              │
│  活力区间   │                                      │              │
├────────────┴──────────────────────────────────────┴──────────────┤
│  ⏱ 2015 ─────────●─────────────────── 2026    [▶ 播放] [1x ▾]    │  ← 时间轴
├──────────────────────────────────────────────────────────────────┤
│  💬 用一句话提问，例如"语序是 SOV 且浏览量在增长的语言"   [🎤]      │  ← NL 入口
└──────────────────────────────────────────────────────────────────┘
```

**导航要点**

1. **时间轴常驻底部**——它是全局变量，切换主视图时不应消失
2. **NL 入口常驻右下角**——它是"输入方式"，不是某个页面的功能
3. **主视图可切换**，但筛选状态与时间轴位置在所有视图间保持（这是联动的基础）
4. **故事模式**时，左侧筛选面板折叠，改为引导文案 + "下一步"按钮

## 7. 模块化结构（对应老师注意点 3：书本与实验结合）

每个模块显式标注课程知识点，答辩时能直接说"这个模块对应书上的第 X 章"。

| 模块 | 内容 | 书本/课程对应点 |
|---|---|---|
| `M1 数据层` | 采集管道 + SQLite + 宽表构建 | 数据获取与清洗 |
| `M2 地图模块` | 2,662 语言点位（有坐标 2,662） + 特征着色 + 下钻 | 地理空间可视化 |
| `M3 时间模块` | 多语言 10 年演变（主题河流 / 多线） | 时间序列可视化 |
| `M4 特征矩阵` | 192 特征 × 语言热力图、特征共现网络 | 高维数据 / 矩阵可视化 |
| `M5 谱系树` | 语系树 + 特征演化着色 | 层次与网络可视化 |
| `M6 条件对比` | 特征分组的小倍数并排对比 ⭐签名 | 多视图协同 / 小倍数 |
| `M7 时间轴回放` | 全局时间控制 ⭐签名 | 动态可视化 / 动画 |
| `M8 NL 交互` | 大模型 → 结构化筛选 → 联动 → 解释 | 高阶人机交互 |
| `M9 输入槽` | 可插拔输入适配器（本期只挂 NL 文本；语音/图像留接口） | 高阶人机交互 |
| `MX 扩展位` | 见 §10（方言 / 特征识别 / 趣味对比），架构上预留给它 | — |

**架构分层**

```
src/
├── data/        采集脚本、SQLite、导出的 JSON
├── stores/      Pinia：全局筛选状态、时间位置、选中语言
├── components/  M2~M7 各视图模块（每个自包含）
├── interactions/ 签名交互（时间轴、条件对比）与 NL 管道
├── theme/       design tokens、ECharts 自定义主题
└── views/       布局与导航（故事模式 / 探索模式）
```

**关键约定**：所有视图**只读 store、不互相直接调用**。这样新增一个视图不需要改其他模块，
也保证了"任一处选中、全局同步"的联动效果。

## 10. 扩展空间（本期不做，但架构必须留口）

这四个方向都不确定要不要做，所以**不写实现，只写"现在必须做对的决定"**。
下面每条都标注了：如果现在不做这个决定，将来要付出什么代价。

### 10.1 中国方言

**设想**：把粒度从"语言"下沉到"方言/土话"（如官话、吴语、闽南语及其次方言）。

- **数据可得性**：Glottolog 的汉藏语系下收录了大量汉语变体（每个都有 Glottocode）；
  另有 CLDF 体系的汉语方言数据集与中国语言资源保护工程的产出可用
- **现在必须做对的决定**：**语言主表用 WALS 的 `ID` 作主键（记为 `wals_id`），
  `Glottocode` 作为非唯一的语言级分组键**
  - ⚠️ **这条在实测后被更正过**。最初的设计是"用 Glottocode 作主键"，
    理由是方言通常没有独立 ISO 码。但实测发现 **WALS 里 Glottocode 根本不唯一**：
    2,662 条真语言记录只有 2,502 个 Glottocode，**93 个 Glottocode 覆盖 2~6 个不同变体**
    （`basq1248` 有 11 个变体；`stan1295` = 标准德语 + 伯尔尼德语 + 苏黎世德语…），
    且 **90/93 组的特征取值互相冲突**。
  - 后果：按 Glottocode 作主键并用 `aggfunc="first"` 透视，会**静默合并 236 条
    变体记录、丢掉 560 行特征数据**（已实测：75,915 行 → 修正后 76,475 行，
    覆盖语言 2,518 → 2,660）。
  - 正确做法：`wals_id` 作主键（唯一，3,573 行；其中真语言 2,662 行），
    `glottocode` 建索引用于
    **上卷到语言层级**。这样反而获得了**两个粒度**——变体级分析 + 语言级聚合，
    比原来只有一层更好。
  - ⚠️ **另一条实测更正（P4 阶段发现）**：`languages.csv` 的 3,573 行里混有
    **911 行语系 / 语族 / 语支的层级占位行**（ID 形如 `family-abun`、
    `genus-berber`、`subfamily-chadic`），它们不是语言。
    `dim_language` 保留全部原始行并标注 `kind`，
    但导出给前端的 `languages.json` 只含 2,662 门真语言 ——
    否则顶栏"语言数"虚高约 900，语系筛选还会多出一个巨大的"未分类"桶，
    搜 "Chadic" 也会搜出语系占位行。
- **附带好处**：需要挂中国方言时，新增行给出各自的 ID 与 Glottocode 即可，
  既保留方言粒度，也能按 Glottocode 聚合回汉语层级

### 10.2 根据特征识别语言（趣味交互）

**设想**：用户勾选几个语法特征（"有声调""SOV 语序""名词有格标记"），
系统推荐最符合的语言——类似"语言连连看"。

- **实现成本**：**低。** 不需要训练模型，就是特征向量相似度（加权 Jaccard / 汉明距离）
- **现在必须做对的决定**：**额外物化一张 `feature_vector` 表**
  - 每个语言一行、192 列、缺失值单独用掩码标记
  - 代价（如果做错）：将来做这个功能时要在前端实时把 76,475 行长表透视成宽表，
    每次查询都要算，体验会卡；而且缺失值的语义（"该语言没有这个特征"
    vs "WALS 未收录"）会丢失，导致推荐结果错误
- **额外好处**：这张表同时会加速 §3 的**条件对比交互（#6）**——它本来就需要按特征分组

### 10.3 趣味性多语言对比

**设想**：选 2~4 种语言并排对比结构特征、10 年活力曲线、文化背景。

- **现在必须做对的决定**：
  1. store 里**同时保留 `selected`（单个）和 `comparisonSet`（多个）两种状态**，
     而不是只有一个"当前选中语言"
  2. 语言卡片组件设计成**可并排、可缩窄**，而不是只适配全宽单卡
  - 代价（如果做错）：所有视图的选中逻辑要重构，卡片尺寸假设要全部推翻

### 10.4 语音 / 音频 → 语言识别

**设想**：用户说一段话，据发音特征判断**可能是哪种语言**。
（这比"语音转文字再提问"有意思得多，但需要独立的声学模型。）

- **数据/模型可得性**：不确定，需要专门找 spoken language identification 模型
- **现在必须做对的决定**：**右下角输入入口抽象成 `InputAdapter` 接口**
  ```
  InputAdapter: { type: 'text' | 'audio' | 'image', accept(): Intent }
  ```
  本期只实现 `text`，但接口先定好
  - 代价（如果做错）：NL 查询管道会和文本框耦合，将来接音频要重写查询层

### 10.5 让上述扩展变简单的五个架构约定

| # | 约定 | 服务于 |
|---|---|---|
| 1 | 主键用 `wals_id`（唯一）；`glottocode` 是非唯一的分组键，可上卷到语言层级 | 10.1 方言、10.3 语言级聚合 |
| 2 | 物化 `feature_vector` 宽表（192 列 + 缺失掩码） | 10.2 特征识别、§3 交互 #6 |
| 3 | 主视图用**注册表模式**注册，新增视图不改动其他模块 | 所有扩展 |
| 4 | 输入入口抽象为 `InputAdapter` | 10.4 语音、未来图像 |
| 5 | store 同时维护 `selected` 与 `comparisonSet` | 10.3 多语言对比 |
| 6 | 跨源关联的不确定性要**显式落库**（`join_ambiguous` / `iso_candidates`） | 数据可信度与答辩可复核 |

> 这五条**全部是零成本或极低成本**的现在就做的决定，
> 但它们决定了将来加功能是"加一个模块"还是"重做数据层"。
